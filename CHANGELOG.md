# Changelog of neocarta library and MCP server


## Upcoming

### Documentation
- `CLAUDE.md` now documents the **Google** docstring convention (matching the Ruff `pydocstyle` config that CI enforces) instead of numpy, which `make lint` actually rejects. (#276)
- Added `REVIEW.md` (repo-root, review-only guidance encoding Neocarta's review uniques) and a `## Code Review` section in `CLAUDE.md` nudging contributors to the `/code-review` skill and the managed `@claude review` flow. (#278)

### Fixed
- `DatabricksSchemaExtractor.extract_column_unique_values_for_table` no longer accumulates duplicate sampled values in its cache when called more than once for the same table with `cache=True`; the cached values frame is now de-duplicated by `value_id`, so repeated calls can't produce duplicate `:Value` nodes / `HAS_VALUE` edges. It also now warns when no column metadata is available (so non-sampleable complex types can't be detected), instead of silently pushing a complex column into a `collect_set` query that Databricks would reject.
- `DatabricksSchemaExtractor` now rejects a `catalog` containing a backtick at construction (a `ConfigError`), matching the up-front `schema` validation, instead of only failing when the first query reaches identifier-quoting.
- `DatabricksSchemaTransformer.transform_to_references_relationships` no longer re-filters on `constraint_type == "FOREIGN KEY"` (the extractor already emits foreign-key rows exclusively); the redundant filter was also a latent `KeyError` on a column-less empty frame. It now iterates the references frame directly and tolerates an empty frame that carries no `constraint_type` column.
- `write_embeddings_to_graph` now logs the actual number of embeddings written based on input row count, instead of `summary.counters.properties_set`, which is always 0 because `db.create.setNodeVectorProperty` is a procedure call and Neo4j query summary counters do not track procedure-call writes. (#216)
- Connector skills now document search-entry-point index requirements and embedding label obligations. Any node label used as an MCP search entry point must have a full-text index created at load time and must be included in the CLI `--embeddings` label set. Override hazard for `Neo4jRDBMSLoader` subclasses is now explicit in the contract. (#211)

### Changed

- `is_primary_key` / `is_foreign_key` on `Column` class are now optional fields for connectors that don't provide these fields, such as the Unity Catalog connector.

### Added
- `DatabricksSchemaConnector` (`neocarta.connectors.databricks`): an in-process source connector that ingests **schema** metadata from managed Databricks Unity Catalog into the core RDBMS data model (`Database`, `Schema`, `Table`, `Column`, `Value` nodes plus `HAS_SCHEMA` / `HAS_TABLE` / `HAS_COLUMN` / `HAS_VALUE` / `REFERENCES` edges). It reads a catalog's `<catalog>.information_schema.*` views over a Databricks **SQL warehouse** using the official pure-Python `databricks-sql-connector` (DB-API 2.0) — **no Spark, no JDBC, no cluster** — and pulls results into pandas, mirroring the BigQuery schema connector (`extract` → `transform` → `load` → `upsert_neocarta_graph_node`, with `StateError` on out-of-order calls). A catalog maps to `Database` (analog of the BigQuery project, a constructor arg, `platform="DATABRICKS"` / `service="UNITY_CATALOG"`), a schema to `Schema` (passed per `ingest(schema=...)` call — one schema per call), tables and views to `Table`, and columns to `Column`; declared primary/foreign keys (Unity Catalog constraints are informational, not enforced) set the column key flags and produce `REFERENCES` edges. Sample distinct column values (`:Value` / `HAS_VALUE`) are read on by default and skip complex types (ARRAY/MAP/STRUCT/BINARY/VARIANT); because that is the only stage that reads table *data* (warehouse cost / data-read grants / PII), it can be disabled with `value_sample_limit=0`. Every query is scoped to the target catalog (`WHERE table_catalog = <catalog>`), so the account-wide `system.information_schema` cannot leak other catalogs' objects and the emitted nodes stay internally consistent under one `Database`. A runnable example lives in [`examples/databricks_schema.py`](examples/databricks_schema.py). The caller constructs and owns the `databricks.sql` connection (mirroring how the BigQuery connector takes a `client`), so `close()` is a no-op and never closes it. `databricks.sql` exceptions are mapped to typed neocarta errors by `databricks/_errors.py`, classified by exception **class** only — a `ProgrammingError` (invalid SQL/request) becomes a `ConfigError`, every other genuine `databricks.sql` error a `retryable`-tagged `ExtractionError` — never by matching error-message text (which is not an API contract). All node ids route through `connectors/utils/generate_id.py`. PAT auth for v1 (OAuth M2M is a documented follow-up). Ships behind the optional `databricks` extra (`databricks-sql-connector` added alongside the existing `databricks-sdk`; a Spark-based variant stays a separate future extra). Covered by mocked-connection unit tests (conformance + extract + transform); a live-warehouse integration test is intentionally excluded from CI. The `neocarta databricks schema` CLI command is a planned follow-up.
- Neo4j connection settings can now be overridden per invocation with the `--neo4j-uri`, `--neo4j-username`, and `--neo4j-database` flags on every connector command (`bigquery schema` / `logs`, `csv ingest`, `dataplex schema` / `glossary`, `jdbc schema`, `osi ingest` / `export`, `query-log ingest`), taking priority over the `NEO4J_URI` / `NEO4J_USERNAME` / `NEO4J_DATABASE` env vars (resolution order: flag > env > default). The password remains env-only (`NEO4J_PASSWORD`, never a flag) so the raw secret never lands in a named local variable, shell history, or the process list — mirroring the `JDBC_PASSWORD` discipline. The shared `neo4j_options` decorator and `_apply_neo4j_overrides` helper in `_cli/commands/_common.py` keep the flags consistent across commands, and `agent-context` surfaces them automatically. Closes #222.
- The BigQuery schema connector now hard-codes `platform="GCP"` and `service="BIGQUERY"` on all `Database` nodes it emits. These values are static for BigQuery and were previously left unset (`None`). (#190)
- `neocarta tool <tool>`: every Neocarta MCP server tool is now also a first-class CLI command, mirroring the server by **name, arguments, and documentation** (#164). The group is named `tool` (not `mcp`) because no MCP server is involved — the commands run directly against the CLI's Neo4j driver. The `neocarta tool` group exposes the three catalog tools (`list-schemas`, `list-tables-by-schema`, `get-full-metadata-schema`) and all nine search tools (`get-context-by-{table,column}-{vector,full-text,hybrid,business-term-hybrid}-search` plus `get-context-by-schema-and-table-vector-search`); each command name is the kebab-cased tool name, each `--help` is the tool's docstring, and the `--text-content` / `--max-tables` / `--search-top-k` flags (with the same per-tool defaults) and `--schema-name` mirror the tool signatures, all surfaced through `neocarta agent-context`. The commands reuse the same Cypher builders (`neocarta._mcp.cypher`), result models (`neocarta._mcp.models`), Lucene sanitiser, and `LiteLLMEmbeddingsConnector` the server uses, run synchronously against the CLI's Neo4j driver, and emit the standard `{ "tool_<tool>": { ..., "count", "results" } }` JSON envelope. Unlike the server's async, index-gated single-tool-per-label registration, the CLI exposes all tools statically; a search command run against a graph missing the required vector/full-text index fails cleanly with exit code `3` (`not_found`), and a failed query embedding maps to `8` (`upstream_error`). The catalog commands need only `[cli]` and `NEO4J_*`; the embedding-backed search commands additionally need an embedding-provider key (e.g. `OPENAI_API_KEY`) and read `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` so query and stored vectors agree. No `fastmcp` / `[mcp]` extra is required to call these commands. Ships unit tests in `tests/unit/_cli/test_tool.py`. Closes #164.

- **Governance-tag data model** (`neocarta.data_model.governance`): a new, vendor-neutral component for modelling governance tags (controlled-vocabulary labels used for policy/classification/ownership) in their own right, rather than forcing them into the business glossary (`Glossary` / `Category` / `BusinessTerm`), where a tag's values are not business *terms*. It has two layers. **Definition:** `GovernanceTagKey {id, name, description, embedding}` —`[:HAS_VALUE_OPTION]`→ `GovernanceTagValue {id, name, description?}` describes which tags exist, what they mean, and (when governed) which values are allowed; the key is the agent-searchable surface (full-text index over name+description, plus an optional vector index). **Instance:** `(:Column|:Table|:Schema)` —`[:TAGGED_WITH]`→ `GovernanceTag {id, key, value}` records where tags are applied (one assignment node per tagged object), optionally —`[:HAS_DEFINITION]`→ `GovernanceTagValue` when the applied value is governed (a missing link marks a free-form value, enabling tag validation). Node ids are namespaced by source so keys/values don't collide across accounts or vendors; `GovernanceTagValue.description` is optional because some platforms (GCP resource Tags) describe values while others (Databricks, Snowflake) leave them bare. `Neo4jRDBMSLoader` gains `load_governance_tag_key_nodes` / `load_governance_tag_value_nodes` / `load_governance_tag_nodes`, `load_has_value_option_relationships` / `load_has_definition_relationships`, and `load_{column,table,schema}_tagged_with_governance_tag_relationships`.

- `DatabricksTagsConnector` (`neocarta.connectors.databricks`) and the `neocarta databricks tags` CLI verb: a source connector that ingests managed-Databricks Unity Catalog **governed-tag definitions** into the governance-tag model. It reads tag policies via the Databricks SDK (`WorkspaceClient.tag_policies`) — **no SQL warehouse or cluster required**, only a workspace host and token — and emits the definition layer: a `GovernanceTagKey` per tag key (carrying its description), a `GovernanceTagValue` per allowed value (name only — Databricks values are bare), and a `HAS_VALUE_OPTION` edge between them. Ids are namespaced by the workspace metastore id (overridable with `--source`, falling back to the host). Platform/partner-managed governed tags — those whose key matches one of the configurable `--system-prefixes` (default `system.`, `class.`, `ai.`, `sap.`, covering Databricks system tags, auto-applied data classifications, `system.ai` model tags, and SAP Delta Sharing tags) — are excluded unless `--include-system-tags` is set; value-less tags become a key with no value options. `--embeddings` embeds `GovernanceTagKey.description` via LiteLLM. Ships behind the optional `databricks` extra (`pip install neocarta[databricks]`); when the extra is missing the command fails with a clean `usage_error` and an install hint (mirroring `neocarta mcp serve`) rather than an `ImportError` traceback. Tag *assignments* (the instance layer, from `information_schema.*_tags`, which needs a SQL warehouse) are a planned follow-up.

- `neocarta mcp serve`: a CLI command that starts the Neocarta MCP server over stdio from inside the main `neocarta` CLI — the CLI-native equivalent of the standalone `neocarta-mcp` console script (both delegate to `neocarta._mcp.server.run`). It reuses the same environment configuration (`NEO4J_URI` / `NEO4J_USERNAME` / `NEO4J_PASSWORD` / `NEO4J_DATABASE`, `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS`). The server is provided by the optional `mcp` extra, so the command additionally requires `mcp` to be installed alongside the `cli` extra; when `mcp` is missing it fails with a clean `usage_error` and an install hint (`pip install 'neocarta[mcp]'`) rather than an import traceback, and a missing Neo4j configuration is reported as a `usage_error` before the server starts. Because the stdio server owns stdout for the MCP protocol, the command writes only a startup notice to stderr (no stdout result payload); `--json` therefore applies only to `--dry-run`, which prints the planned transport/database/embedding configuration without starting the server.

- All connectors now support the context-manager protocol (`__enter__` / `__exit__` / `close()`), so a connector can be used as `with FooConnector(neo4j_driver=driver) as connector: connector.ingest(...)`. `close()` releases only resources the connector itself created and owns (e.g. the Unity Catalog connector's `httpx.Client`); the **injected Neo4j driver is owned by the caller and is intentionally left open**, so sharing one driver across connectors or reusing it after the `with` block is safe. Connectors that only hold the injected driver have a no-op `close()`. (Documented in `connector-contract.md` §9b and exercised by the per-connector conformance tests.)

- The OSI loader now creates full-text indexes on all of its search nodes — `Domain` (`OsiSemanticModel`), `Table`, `Column`, `Metric`, and `BusinessTerm` — at load time (mirroring how `Neo4jRDBMSLoader` does for the core RDBMS labels). The OSI loaders override the base Table/Column loaders (and `OsiSemanticModel` previously created no index at all), so a pure-OSI graph had none of `domain_/table_/column_/metric_/businessterm_full_text_index`, leaving the MCP full-text, hybrid, and business-term-bridged search tiers unregistered. (`:OsiSemanticModel` / `:OsiTable` / `:OsiColumn` augment the core `:Domain` / `:Table` / `:Column` nodes and back the same search surface.) `osi ingest --embeddings` now also embeds `Metric.description` and `Domain.description` (in addition to the shared `Database`/`Schema`/`Table`/`Column` labels), creating `metric_vector_index` / `domain_vector_index` so the vector and hybrid metric- and domain-search tiers register.

- `UnityCatalogSchemaConnector` (`neocarta.connectors.unity_catalog`): a source connector that ingests structural metadata (`Database`, `Schema`, `Table`, `Column` nodes plus `HAS_SCHEMA` / `HAS_TABLE` / `HAS_COLUMN` edges) from the **open** Unity Catalog REST API (`/api/2.1/unity-catalog`, the Apache-2.0 project at github.com/unitycatalog/unitycatalog — not the Databricks SDK), so it works against any conformant Unity Catalog server. Catalogs map to `Database`, schemas to `Schema`, tables and views to `Table` (the UC `table_type` is recorded during extraction but views are not modeled as a distinct node label), and each table's inline `columns` to `Column`. The connector owns its `httpx.Client` and is usable as a context manager (or via `close()`) to release the connection pool. The open UC API exposes no primary/foreign-key constraints, so `is_primary_key` / `is_foreign_key` are left null (unpopulated) and no `REFERENCES` edges are produced; no value sampling or glossary/tags are performed.


## v0.8.0

### Fixed

- Embeddings-related environment variables (`EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS`, `EMBEDDING_BATCH_SIZE`) are now respected consistently across the library, CLI, and MCP server (#187). Previously `EMBEDDING_BATCH_SIZE` was read into CLI settings but never passed to the embedder, so it had no effect; the CLI `_run_embeddings` helper now threads it through to `run()`. Setting `EMBEDDING_DIMENSIONS` on a model that does not support dimension truncation no longer crashes the run with a misleading credentials error — when the provider rejects the value (e.g. OpenAI `text-embedding-ada-002`), the connector transparently drops `dimensions` and retries, so the run succeeds and the vector index is created at the model's probed (native) dimension. (LiteLLM's per-call `drop_params` is not honored on the embeddings path, so the fallback is handled in-connector.) The MCP server now also reads `EMBEDDING_DIMENSIONS` and passes it to its query embedder, so query and stored-vector dimensions agree.

### Changed

- **Refactor (breaking import paths):** the `neocarta.data_model` package is reorganised by layer of concern instead of one module per source. `schema/` holds the structural models, partitioned into `schema/rdbms` (was `data_model.rdbms.core`) and `schema/lpg` (was `data_model.lpg`); the remaining concerns are split out of the old `rdbms.expanded` junk-drawer into `glossary/`, `instance/` (`Value` / `HasValue`), `query/` (`Query`, `CTE`, `USES_*`, `DEFINES`), and `osi/` (semantic-model nodes and relationships). `NeocartaGraph` moves to `metadata/models.py` (the `from neocarta.data_model.metadata import NeocartaGraph` path is unchanged). Each module exposes a `models.py` plus a `README.md`. The duplicated `field_validator` bodies are extracted into shared helpers in `data_model/_validators.py`. The `Value` node is now source-agnostic (one model, the string-cast shape) with `HAS_VALUE` carrying the source entity; the in-progress LPG `(:Property)-[:HAS_VALUE]->(:Value)` edge is deferred. No back-compat shims are provided: import from the new module paths (e.g. `from neocarta.data_model.schema.rdbms import Table`, `from neocarta.data_model.glossary import BusinessTerm`). Behaviour of the models (fields, validation, wire format) is unchanged. Closes #167.
- **Behavior change:** `neocarta bigquery schema` now defaults to `--no-embeddings`, matching every other ingest command (`bigquery logs`, `dataplex schema` / `glossary`, `csv ingest`, `osi ingest`). Embedding generation is strictly opt-in via `--embeddings`, so a plain schema ingest no longer makes embedding-provider API calls (cost + latency) unless requested. Pass `--embeddings` to restore the previous behavior. Closes #186.
- Connector and ingest progress is now reported through Python's `logging` (rooted at the `neocarta` logger) instead of bare `print()`. Connectors log each ETL phase (`extract` / `transform` / `load`) with per-type produced-object counts; the Neo4j loader logs each write by its graph pattern plus merge counters (e.g. `Ingested (:Column)-[:TAGGED_WITH]->(:BusinessTerm) — created 12, properties_set 24`); and each extractor method logs a one-line summary (target + row count + elapsed). SQL text and row values are never logged. The bare `print()` calls in the connectors, the ingest layer, and the query-log/SQL-parsing utilities were converted to module loggers (`logging.getLogger(__name__)`), and the error `print()`s in the Dataplex glossary extractor became `logger.warning`. Importing neocarta as a library stays silent (a `NullHandler` is attached to the `neocarta` logger); only the CLI attaches a real handler.
- The embeddings/enrichment subsystem now uses the same `logging` system. `BaseEmbeddingsConnector` logs the detected embedding dimension + model, a per-label `Embedding <Label> nodes…` line, the embedded-description count, and (via `write_embeddings_to_graph`) `Wrote N embeddings to (:Label)`; per-batch progress is logged at DEBUG. The provider `_create_embedding*` error `print()`s in the LiteLLM and OpenAI connectors became `logger.warning` that log the **exception type only** (`Embedding request failed (BadRequestError)`) — the provider error body can echo the offending input description or a masked API key, so it is never logged, mirroring the query-log SQL-parse handler. Description text and embedding vectors are never logged (only counts, labels, dimensions, and batch indices).
- The `add-source-connector` Claude Code skill is renamed to `neocarta-add-source-connector` (invoked as `/neocarta-add-source-connector`) to namespace it and avoid collisions with other skills; its directory, the `connector-contract.md` references in `neocarta/connectors/_base.py`, the connector conformance tests, and the README were updated accordingly. The skill's contract and scaffold now document and generate the `logging`-based progress reporting (new contract §16): scaffolded extractors decorate `extract()` with `@log_stage`, and scaffolded connectors define `_TRANSFORM_COUNTS`, call `log_transform_counts`, and log each phase through a module logger instead of `print()`. The skill's `verify` now also warns on any stray `print()` in connector code (alongside the existing inline-id-f-string warning).

### Added

- OSI tooling on the MCP server: the OSI (Open Semantic Interchange) layer of the graph — Domains (`OsiSemanticModel`) and Metrics, plus the Expressions and Aspects hanging off them — is now reachable by AI agents, mirroring the existing RDBMS tool surface. New tools register only when an OSI model is present (gated on a new `has_osi_nodes` probe for the `:OsiSemanticModel` label): **reference** — `list_domains` (with metric/table/column/join counts) and `list_metrics_by_domain`; **domain context** — `get_domain_context(domain_name)` (the scoped, OSI-aware counterpart to `get_full_metadata_schema`); **metric entry-point search** — `get_context_by_metric_{vector,full_text,hybrid,business_term_hybrid}_search`, driven by the existing `_select_search_strategy` ladder (the `Metric` label is added to the per-label registrars and keyed on the `metric_vector_index` / `metric_full_text_index` indexes), each accepting an optional `domain_name` filter and returning a `MetricContext` (owning domain, dialect-specific expressions, business-term synonyms, aspects); and **definitions** — `get_metric_expression(metric_name, domain_name=None, dialect=None)`. OSI **aspects** (`ai_context` / `custom_extensions`) are not a standalone tool: they ride along on the context payloads — `DomainContext` and its embedded tables, columns, metrics, and joins (`DomainJoinContext.aspects`), plus the table/column search hits — so an agent receives them with the entity it asked for, with no separate addressing scheme to get right. The existing table/column search tools are additionally enriched so a hit also surfaces OSI column expressions (`ColumnContext.expressions`) and table/column aspects (`TableContext.aspects` / `ColumnContext.aspects`) via additive `COLLECT` sub-queries that come back empty on non-OSI graphs (no registration changes, single query path). `get_domain_context` and `list_domains` cover both table-backed and query-backed datasets (`HAS_TABLE`/`HAS_QUERY`, `HAS_COLUMN`/`USES_COLUMN`), and `TableContext`/`ColumnContext` additionally surface OSI richness — `TableContext.primary_key`, `ColumnContext.label`, and `ColumnContext.is_time_dimension` (empty/null on non-OSI graphs). All name→id resolution routes through `connectors/utils/generate_id.py`. New Pydantic models (`MetricContext`, `DomainContext`, `DomainJoinContext`, `ExpressionContext`, `AspectContext`, `ListDomainRecord`, `ListMetricRecord`) and cypher factories (`neocarta/_mcp/cypher/osi_*`). Ships unit tests for the metric strategy ladder + OSI cypher builders and integration tests loading `datasets/osi/acme_semantic_model.yaml` (plus a query-backed-dataset model) with mock embeddings. Closes #189.
- `dimensions` is now a first-class constructor argument on `LiteLLMEmbeddingsConnector` (mirroring `OpenAIEmbeddingsConnector`), replacing the need to pass it through `litellm_kwargs`. It is sent to the provider; if the model does not support truncation the connector catches the rejection, drops `dimensions`, and retries with the native dimension (LiteLLM's per-call `drop_params` is not honored on the embeddings path, so the fallback is handled in-connector).
- `EMBEDDING_DIMENSIONS` and `EMBEDDING_BATCH_SIZE` added to the CLI `agent-context` env-var contract, and all embedding-capable CLI commands gain an `--embedding-batch-size` flag. `bigquery logs` and `osi ingest` gain the previously-missing `--embedding-model` / `--embedding-dimensions` flags (and `osi ingest` now routes embedding through the shared `_run_embeddings` error wrapper). `EMBEDDING_DIMENSIONS` is respected by the MCP server again (re-added to MCP settings after its v0.6.0 removal); `EMBEDDING_BATCH_SIZE` intentionally does not apply to the MCP server, which embeds a single query at a time.
- Unified logging configuration in `neocarta._logging`: `configure_logging(level, *, console=...)` configures the `neocarta` package-root logger (attaching a `rich.logging.RichHandler` to the CLI's existing stderr console when given, so `--no-color` is honored and stdout stays clean for `--json`); plus a `log_stage` decorator and `log_timing` context manager used to instrument extractor methods consistently.
- `--log-level [DEBUG|INFO|WARNING|ERROR]` global CLI option controlling diagnostics verbosity on stderr (default `INFO`). The previously-unused `--debug` flag is now a convenience alias for `--log-level DEBUG`.
- `JdbcSchemaConnector` (`neocarta.connectors.jdbc`): a source connector that extracts schema metadata (`Database`, `Schema`, `Table`, `Column`, and `REFERENCES` foreign-key edges) from any JDBC-compatible database (PostgreSQL, MySQL, Oracle, SQL Server, Redshift, …). The Java↔Python bridge shells out to the SchemaCrawler CLI's `template` command with a bundled FreeMarker template (`schema/catalog.json.ftl`) that renders a compact JSON catalog with full table/column/primary-key/foreign-key detail, then flattens it into the shared `Neo4jRDBMSLoader` pipeline. (SchemaCrawler's `serialize` JSON omits tables and foreign keys, so the template is required to populate `REFERENCES`.) Host prerequisites — Java 11+, the SchemaCrawler distribution (its `_schemacrawler/lib/*` classpath), a FreeMarker JAR on that classpath, and a JDBC driver JAR — are user-supplied (Java availability is checked at construction; all documented in `neocarta/connectors/jdbc/README.md`). The DB password is passed to SchemaCrawler via the environment, never on the command line. Extraction is scoped with `ingest(schemas=[...])`. Ships unit tests (mocked subprocess + a real captured golden fixture) and a skip-guarded Dockerized-PostgreSQL integration test (`tests/integration/connectors/jdbc/`), plus `examples/jdbc.py` and `JDBC_*` entries in `.env.example`.
- CLI connector commands now show a progress spinner on stderr during the long-running stages (`Ingesting ...` while a connector runs, `Generating embeddings...` while embeddings are written, `Exporting OSI semantic model...` on `osi export`), so a slow ingest visibly indicates it is still working. The spinner shares the stderr console with the existing `RichHandler`, so INFO log lines render above it. It is shown only on an interactive terminal: under `--json`/agent mode, CI, or any non-TTY stderr it is a no-op via the new `neocarta._cli.output.cli_status` helper, so machine output and the `--json` stdout contract are unaffected. Closes #170.
- `neocarta jdbc schema`: new CLI command wrapping `JdbcSchemaConnector`, exposing the JDBC source connector on the CLI alongside `bigquery`, `csv`, `dataplex`, `osi`, and `query-log`. Extracts relational schema metadata (`Database`, `Schema`, `Table`, `Column`, and `REFERENCES` foreign-key edges) from any JDBC-accessible database via SchemaCrawler and loads it into Neo4j. Connection inputs resolve from flags or the `JDBC_*` env vars (`JDBC_URL`, `JDBC_DRIVER`, `JDBC_DRIVER_JAR`, `SCHEMACRAWLER_JAR`, `JDBC_USER`, `JDBC_SOURCE_DATABASE_NAME`, `JDBC_PLATFORM`, `JDBC_SERVICE`, `JDBC_TIMEOUT`), all surfaced through `neocarta agent-context`; the DB password is read only from `JDBC_PASSWORD` (secret), never a flag, matching the connector's "password via the environment, never on the command line" design. Supports `--schema` (repeatable) to scope extraction, opt-in `--embeddings`, `--dry-run`, and the standard JSON/exit-code contract. Closes #198.


## v0.7.0 

### Fixed

- MCP server integration tests (`tests/integration/_mcp/test_server_IT.py`) no longer hit the real embedding provider. The batched-embedding change routes graph enrichment through the new `_create_embeddings_sync` / `_create_embeddings_async` batch methods, but the test `MockEmbeddingsConnector` only overrode the single-item `_create_embedding_*` methods — so the module-scoped `loaded_graph` fixture fell through to `litellm`, erroring all eight tests (a 401 in CI with `OPENAI_API_KEY=dummy`, a dimension mismatch locally with a real key). The mock now also overrides the batch methods.
- Connector lifecycle state-tracking. `extract()` on every connector now resets the downstream `_extracted` / `_transformed` flags so a stale prior `transform()` can't be inadvertently `load()`ed after a second `extract()`. `load()` now checks `_transformed` (not `_extracted`), enforcing the lifecycle rule from `.claude/skills/add-source-connector/connector-contract.md` §9 instead of accepting any extract-followed-by-load sequence.
- Embedding generation now sends one batched request per `batch_size` chunk instead of one request per node, which is much faster on large graphs. The sync and async embedders (`LiteLLMEmbeddingsConnector`, `OpenAIEmbeddingsConnector`) embed each chunk in a single `embedding(input=[...])` call. Closes #173.

### Changed

- **Breaking:** Connector public API standardized. All connectors now expose `extract()` / `transform()` / `load()` as public stages (renamed from `extract_metadata` / `transform_metadata` / `load_metadata`) plus an `ingest()` orchestrator. Format connectors additionally expose `export()` as the sole public method for the export direction; its internal stages (graph read, source-format build, file write) are private. The legacy `run()` entrypoint is preserved on every connector as a thin wrapper emitting a `DeprecationWarning`; it will be removed after approximately three releases.
